# Mac UI runner signing diagnosis

The original locally generated `FORGEUITests-Runner.app` displayed “damaged and can’t be opened.” This was a build packaging/signing defect, not evidence that user approval alone would fix it. Automated Mac UI acceptance was not passed by those attempts.

## Evidence and cause

The original was the runner generated by the local unsigned test build.

| Check | Original | Rebuilt through Xcode signing |
|---|---|---|
| Runner signature identifier | `com.apple.XCTRunner`, inconsistent with generated bundle | `com.personal.FORGE.UITests.xctrunner` |
| Info.plist binding | Not bound | Bound, 83 entries |
| Resource seal | None; `_CodeSignature/CodeResources` absent | Version 2 resource seal, nested test bundle recorded |
| Test plugin signature | Linker-only ad-hoc; no Info.plist/resource seal | Xcode signs the complete `.xctest` bundle |
| Strict recursive verification | Failed: `code has no resources but signature indicates they must be present` | Passed; nested plugin validated; valid on disk and designated requirement satisfied |
| Quarantine attribute | No `com.apple.quarantine`; provenance present | No `com.apple.quarantine`; provenance preserved |
| Test entitlements | Missing on original runner | Xcode-generated sandbox, get-task-allow and testmanager/AX service access |

The prior Mac test builds used `CODE_SIGNING_ALLOWED=NO`. Xcode generated the runner around its prebuilt XCTest agent and inserted FORGE's test plugin, but did not perform the final code-signing steps for that generated bundle. The remaining agent signature was not a valid signature for the completed runner. The unsigned/linker-signed plugin also lacked the bundle seal. Standalone `codesign` and `spctl` both returned the same missing-resource error outside the tool sandbox. Earlier system logs showed AppleSystemPolicy launch denial.

The repair used a fresh DerivedData directory, `CODE_SIGNING_ALLOWED=YES`, `CODE_SIGNING_REQUIRED=YES`, `CODE_SIGN_STYLE=Manual`, `CODE_SIGN_IDENTITY=-` and an empty development team. Xcode logged **Sign to Run Locally**, signed the nested test bundle first, then the complete runner with its generated test entitlements. This uses no Apple account or certificate. Xcode also performs its standard per-build execution registration. No manual security-policy modification, quarantine removal, TCC database edit or global exception was used. Existing project data, prior build outputs and result bundles were preserved.

A standalone Gatekeeper assessment still rejects this ad-hoc artifact as a distribution app. That is recorded explicitly; signature validity and local Xcode launch are separate checks. The repaired runner subsequently launched, established a testmanagerd session, connected to FORGE and executed the workflow assertions. A failed assertion is still a failed acceptance run, even when launch succeeds.

## Observed final acceptance

The fresh scripted run passed all three product tests with zero failures, zero skips and no expected failures. The build log, test log and result bundle were collected together. The portable summary, with the physical host identifier removed, is `docs/verification/macos-ui.json`.

- `testOnboardingAndEvidenceRewardLoop`: real onboarding, starting balances/quests, proof, rewards, history and persistent fixture relaunch.
- `testRevenueReviewRecoveryAndOfflineNavigation`: payment, business total, saved review, recovery and offline navigation.
- `testSkillEvidenceAndLargeTextLightAppearance`: Mac light appearance, actual Practicing menu selection, proof, save and reopen. Largest Dynamic Type is an iPhone test condition.

This result contains three internal quality-of-service priority-inversion warnings. Nonfatal debugger `noURL` and DisplayManager diagnostics also appeared in the console. These warnings are retained, not represented as a warning-free run. Prior launch failures and harness assertion failures remain failed attempts; only this executed, passing suite establishes automated Mac acceptance.

## Reproduction

From the repository root:

```sh
bash scripts/verify_mac_ui.sh
```

This creates fresh temporary build/evidence directories, builds and signs with Xcode, verifies both complete bundles recursively, then runs the three product workflows. The native editor diagnostic control is outside this product acceptance suite. The script requires an actual Passed result with three passing tests, zero failures and zero skips; launch alone cannot succeed the script. No assertion is skipped or weakened. `FORGE_MAC_UI_DIR` can select a fresh evidence directory. Existing result evidence is never overwritten or deleted. `FORGE_UI_MAC=1 ./scripts/verify_release.sh` adds this check to the full release verification.

Tests use `--ui-test`, memory stores or a UUID-specific temporary persistent fixture. Each script run uses a unique app/test bundle identity to isolate saved window state. The app now exposes its native New Window command. If Xcode starts it without a window, XCTest invokes that command with Cmd-N and asserts that the actual SwiftUI window exists. Mac assertions read native accessibility values, the skill picker uses its real PopUpButton role, and payment submission has a unique accessibility identifier. Fixture windows and scrollable controls must actually be present and reachable. Real app data and credentials are not used.

If a future machine denies Accessibility or developer-tool access, allow only the specific developer/test application through the normal macOS settings, and rerun. Do not mark Mac UI acceptance passed until the runner executes all three workflows and the result bundle confirms passing assertions.

Apple references: [Code Signing Tasks](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html) explains inside-out nested signing and verification; [TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements) identifies Xcode's Sign to Run Locally as ad-hoc signing.
